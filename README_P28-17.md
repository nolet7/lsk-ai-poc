# P28-17 — Controlled Dockerless EC2 release migration (offline-first)

## What works
- `phase28/ec2_rollout.py` implements an explicitly invoked legacy-directory-to-release-link migration with best-effort restoration on failed restart/health probe; **Linux/POSIX only**.
- A release-aware launch script pairs `/opt/lsk-phase28/releases/<full sha>` with `/opt/lsk-phase28/venvs/<same sha>`.
- `prepare-venv.sh` installs from an **operator-provided, approved local wheelhouse and hashed lock file** with `--no-index --require-hashes`. No dependency lock or wheelhouse is generated by this package. A third-party supply-chain approval is still required.
- The proposed `lsk-phase28-v2.service` remains diagnostic-only, loopback-only, non-root, and disables model inference.
- No Docker, Terraform apply, AWS API calls, remote deployment, privileged OS changes, or inference execution.

## Important integration constraints / TASK before operating on EC2
1. Confirm **Linux CI passed all tests**. This repository's `.github/workflows/phase28-p14-ci.yml` already runs the suite on Ubuntu; do not claim CI success solely from local Windows testing. The new `.github/workflows/phase28-p17-ci.yml` adds explicit shell and release test gates.
2. Review and pin a full Git SHA; separately verify code integrity and approval. Obtain an approved **fully hash-locked** requirements file and wheelhouse matching the release; this package deliberately supplies neither.
3. Do not attempt legacy migration while systemd is running or without exclusive lock. `migrate_legacy()` is a library function, not an executable operator command; the service must first be stopped and a supervised wrapper written and reviewed. Existing `install-from-checkout.sh` is *not* compatible with symlinked releases and must not be rerun afterward.
4. Install `run-current.sh` under `/opt/lsk-phase28/bin` with owner root, mode 0755. Install and review `lsk-phase28-v2.service` as `/etc/systemd/system/lsk-phase28.service` **only after** an approved environment and migration runbook are prepared. Do not replace the live unit yet.
5. Invoke migration only after staging with `release_manager.py` and preparing a matching revision virtual environment. Use supervised service restart and `_diagnostic_probe` callbacks; verify `current` target and preserved `legacy-current-backup`.
6. Validate `systemd-analyze verify`, `nginx -t`, listening sockets, SSM access, service user permissions, journal logs and health; explicitly test rollback. Shared P28-15 `/opt/lsk-phase28/venv` remains intact for legacy recovery.
7. No public ingress, no business APIs, no live Bedrock; `/health/live` expected 200, `/health/ready` expected 503.

**Scope:** This is an offline-tested migration foundation, NOT a completed or live AWS rollout. It intentionally does not perform migration automatically or enable provisioning. Next step is a reviewed, executable SSM change-window operator workflow with OS preflight, lock ownership, and external service health checks.
